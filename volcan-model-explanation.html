01 · What Vulcan Is
❯
The question that started this
Tell me about Razorpay's Vulcan.

A foundation model for the language of money movement

Vulcan is Razorpay's proprietary, transformer-based AI model, purpose-built to understand transaction patterns and optimize digital payments across India. Instead of processing words, it processes payment events — checkout, routing, risk, and fraud, scored together by one model instead of several disconnected ones.

What it actually does

CapabilityWhat it doesObserved impact
Smart routing Predicts bank downtime, gateway latency and OTP delays, then routes each transaction through the best live path. 8–10% higher transaction success
Fraud detection Flags stolen cards and risky cash-on-delivery orders before checkout completes, at the network level. 8x international card fraud caught, 5x more disputes flagged

Quick-commerce platform Blinkit is already running it in production; Razorpay's stated roadmap extends the same backbone to real-time credit underwriting and custom merchant risk scoring — without retraining the base model.

02 · Why Not Traditional ML
❯
The next question
What's actually different between Vulcan and traditional routing systems?

One shared model, instead of three that don't talk to each other

Most payment gateways run an ensemble of narrow models — one scores fraud, another checks gateway uptime, a third predicts OTP latency — stitched together with hardcoded rules. Because each stage runs in isolation, none of them can learn from the others' context in real time.

Traditional pipeline — three blind models
[Txn Features] ──> Model A: Fraud Score     ──> Hard Gates
[Txn Features] ──> Model B: Gateway Downtime ──> Priority Queues ──> Route Decision
[Txn Features] ──> Model C: OTP Latency     ──> Fallbacks
Vulcan — one shared representation
[~3,000 signals: issuer, VPA, BIN, latency, auth flow, history]
        │
        ▼
 ┌───────────────────────────┐
 │ Self-attention / context   │ ──> unified embedding ──> scored together
 │ (NVIDIA H100 clusters)    │     (health + fraud + checkout, in one pass)
 └───────────────────────────┘

Side by side

DimensionTraditional / rule-based routingVulcan

At runtime this plays out in three steps: Vulcan pre-scores every viable route before a payment is even dispatched; it models latent friction — not just "is the bank up" but "how likely is a slow OTP on this carrier, right now"; and it keeps adapting continuously as billions of transactions settle, with no manual rule maintenance.

03 · Why A Transformer, Specifically
❯
The next question
Why use a transformer architecture for this — why not traditional ML or a regular deep learning model?

Payments are sequences, not spreadsheet rows

A gradient-boosted model like XGBoost treats every transaction as one static row. But a real payment is a stream of events over time — a session, a retry, a bank hop. Capturing that history in tabular ML means hand-building thousands of rolling features, which stops scaling well past a few hundred signals.

Why the alternatives fall short

ArchitectureWhere it breaks at foundation-model scale
XGBoost / LightGBMPoint-in-time only; no shared representation across fraud, routing and checkout — each needs its own model
Plain MLPsTreats features as independent; can't capture how one signal's meaning depends on another
RNNs / LSTMsProcess events one at a time, which is too slow to pre-train across trillions of data points on GPUs
1D-CNNsOnly see nearby events — can't connect an OTP delay on one carrier to a bank's retry logic elsewhere
TransformersEvery signal can attend to every other signal at once, and the math parallelizes cleanly across GPU clusters
WHY THIS MATTERS IN PRACTICE A 400ms latency spike on a bank is negligible for a normal net-banking payment — but can be fatal for a high-concurrency UPI flash-sale checkout using dynamic OTP. Self-attention lets the model weigh that context automatically, instead of an engineer hand-coding the interaction.

One backbone, many downstream tasks

Foundation model paradigm
       [ 3 trillion data points: raw payment sequences ]
                          │
                          ▼
              ┌───────────────────────┐
              │ Pre-trained transformer  │  "language of money movement"
              │ (shared graph embeddings) │
              └───────────────────────┘
           ┌──────────────┼──────────────┐
           ▼              ▼              ▼
   [Routing head]   [Fraud head]   [Checkout head]
   success-path      cross-merchant  method
   ranking           abuse           personalization

This is the real payoff: solving a new problem the traditional way means collecting a fresh dataset and training a model from zero. With a foundation backbone, Vulcan only needs a lightweight new head on top of a model that already understands India's payment rails.

04 · Built From Scratch
❯
The next question
Was this built ground-up, or is it based on an existing model / LLM?

Not a fine-tuned LLM — a transformer trained on money, from zero

Vulcan borrows the mechanics of transformer architecture — multi-head self-attention, sequence embeddings — but it wasn't initialized from an existing language model like GPT or Llama. It was trained from zero weights, and its "vocabulary" was never words to begin with.

 A public LLMVulcan
VocabularyWords and subwordsBank switch states, VPA patterns, OTP latency, tokenization flags
Starting pointPre-trained on internet textZero weights, trained only on Razorpay's own network
Training scalePublic web corpora~3T data points across 4B+ transactions
ComputeVariesNVIDIA H100 clusters, orchestrated on AWS SageMaker

Why an off-the-shelf model couldn't do this

Data privacy and compliance. RBI's data localization rules and India's DPDP Act require financial telemetry to stay on isolated, private infrastructure — ruling out external or cloud-hosted general LLM APIs outright.

Domain structure. Public LLMs have no notion of NPCI switch throttling, multi-hop UPI fallback logic, or dynamic OTP flows. Razorpay had to design its own tokenizers and embedding spaces to represent the graph and time-series structure of Indian payment rails specifically.

05 · Turning Payments Into Tokens
❯
The next question
How does raw payment data actually get converted into tokens a transformer can read?

A tokenizer for money instead of words

Every payment attempt gets converted into a sequence of discrete tokens the transformer can attend over — the payments equivalent of turning a sentence into subwords. Three kinds of signals feed this pipeline.

Tokenization pipeline
[Raw payment telemetry]
   │
   ├─ Categorical  (issuer, gateway, rail, auth type)   ──> vocabulary tokens
   ├─ Continuous   (latency, amount, history)          ──> quantized buckets
   └─ Graph        (VPA handle, merchant, device)      ──> node embeddings
   │
   ▼
[token embedding + temporal embedding + channel embedding]
   │
   ▼
[Transformer self-attention layers]

Three token families

Categorical state tokens — bank BINs, error codes like NPCI_U30, auth types (dynamic OTP, biometric, PIN, 3DS 2.0) — mapped to a fixed vocabulary, the same way words map to a dictionary.

Continuous signals — OTP round-trip latency, transaction velocity, order value — either bucketed into quantile ranges like LATENCY_400_500MS, or passed through linear projection into continuous embeddings.

Graph identifiers — VPA handles, issuer-acquirer pairs, device footprints — pre-embedded with graph methods (Node2Vec, GNNs) so the banking network's topology is preserved before it ever reaches the transformer.

How it learns the pattern

Pre-training objectiveWhat it teaches the model
Masked event modelingHide a token (e.g. the final response code) and predict it from everything upstream — BERT-style
Next-event predictionPredict the next step in a retry/fallback chain, so routing can anticipate failure before it happens
Contrastive trajectory matchingPull normal checkout patterns close together in embedding space, push anomalous ones apart

06 · Speed At Flash-Sale Scale
❯
The next question
How do payments foundation models maintain sub-50ms inference SLAs during flash sales and peak checkout concurrency?

Staying under 50ms with thousands of transactions per second

A 70B-parameter chat model would never survive checkout-time inference. A payments foundation model is deliberately built small, compressed, and split across a sync/async serving pipeline so the GPU-bound part only does the minimum required at the millisecond that matters.

20–150M
parameters — compact vs. a typical 70B+ text LLM
10–15
dense payment tokens per transaction, vs 40+ for BPE text tokens
6–12
attention layers — shallow, to keep O(n²) cost in check
5–15ms
actual GPU inference time on the live signals

What's precomputed vs. scored live

Signal typeEvaluation phaseLatency
Historical / entity embeddingsPrecomputed async via streaming pipelines, cached in Redis/Aerospike-style stores< 2ms (cache lookup)
Live network healthContinuously updated sliding-window aggregation< 1ms
Routing / risk scoringOnly the dynamic features + prefetched embeddings hit the GPU5–15ms (real inference)

Under flash-sale load

Compilation & quantization. The trained model is compiled through TensorRT with kernel fusion and INT8/FP8 quantization, served on NVIDIA Triton — cutting the raw forward pass under 10ms.

Dynamic batching. Incoming requests are batched inside a tight 2–4ms window instead of processed one by one, keeping GPU utilization high without blowing the latency budget.

THE SAFETY VALVE If ingress latency crosses roughly 35ms under extreme traffic, a circuit breaker trips: skip full self-attention, fall back to a lightweight quantized linear classifier or a cached routing matrix, and guarantee the payment still reaches the bank without adding checkout delay.
